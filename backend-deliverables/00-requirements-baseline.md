# 成员 C 后端需求基线

- 文档状态：已确认（第一阶段冻结，含后续明确授权扩展）
- 版本：1.1
- 更新日期：2026-08-05
- 当前阶段：沉浸式分支短剧游戏需求确认

## 1. 项目核心目标

项目最终设想包含两个核心功能：

1. 沉浸式短剧游戏：播放预先制作的视频剧情，在剧情节点提供选项，依据玩家选择跳转到不同视频片段并到达不同结局。
2. 一句话短剧：用户输入故事描述并选择风格、时长等条件，由系统生成短剧或剧本。

当前只优先交付第一个功能。第二个功能必须在沉浸式短剧游戏完成后再单独评估；如果视频生成不可行，可以降级为剧本生成，也可以从原型范围中移除。

## 2. 第一阶段产品流程

1. 用户进入游戏入口并点击“开始游戏”。
2. 系统创建游戏会话并返回入口剧情节点。
3. 前端播放该节点对应的预制视频。
4. 视频播放到该节点的选择点后，前端显示由剧本配置的选项。
5. 用户选择后，后端验证当前会话和选项，记录进度并返回下一剧情节点。
6. 前端立即衔接播放下一节点的视频。
7. 重复上述过程，直到后端返回结局节点。

剧情主题为“沿澳门六个景点步行，破解历史悬案”。整体分为六个章节，每章对应一个澳门景点。首版中的“步行”和景点变化属于剧情表达，不校验玩家真实 GPS 位置。

## 3. 已确认的功能要求

### 3.1 剧情图

- 剧情使用节点和有向分支表示，不采用写死的固定步骤。
- 普通剧情节点的选项一般为 2 至 3 个，但具体数量和文案由剧本编写人员决定。
- 后端不得写死选项数量，应支持：结局节点没有选项，普通节点包含任意合理数量的选项。
- 每个选项指向一个下一剧情节点。
- 多个分支允许重新汇合到同一个剧情节点，以减少视频制作量。
- 部分选项可以发放线索；线索可以影响后续可用内容或最终结局。
- 线索奖励、选项内容和选项数量均由剧本编写人员配置，后端只执行和校验规则。
- 六章内容和最终分支尚未完成，后端需要提供稳定的数据模板供内容人员填写或导入。

### 3.2 视频播放与连续性

- 首版采用“一个剧情节点对应一个独立视频片段”的模式。
- 选择点默认位于视频片段结束处，首版不要求按视频时间码在片段中途暂停。
- 选项出现时，背景必须持续显示当前片段的最后画面，不能出现黑屏或空白背景。
- 用户选择后，应尽快衔接下一片段，避免明显的无画面间隔。
- 后端数据需要为每个剧情节点提供视频资源信息，并为前端预加载候选下一片段提供必要元数据。
- 视频内的旁白、人物对白、文字剧情和字幕由视频制作人员处理，后端不负责生成或叠加这些内容。
- 前端负责播放器末帧保持、选项覆盖层、媒体预加载和实际转场；这些不是成员 C 的页面实现任务。

### 3.3 会话与部署

- 后端必须能够记录每次游戏的当前节点、选择历史、开始时间和完成状态。
- 原型需要部署后供多名评委或体验者访问，不能只在开发者本机运行。
- 当前目标是展示产品想法的原型，不要求生产级账号安全、风控和复杂故障恢复。
- 首版不依赖 GPS；后端数据模型可以预留景点坐标和未来的位置校验扩展字段，但不实现校验逻辑。
- 首版允许匿名开始游戏，不要求登录。
- 浏览器保存匿名会话标识，后端支持在同一浏览器恢复进度；首版不支持跨设备恢复。
- 2026-08-04 已明确授权补充最小登录与注册能力；它不改变匿名游戏可直接开始、也不把匿名游戏进度自动合并到账户的要求。

### 3.4 对象存储与景点介绍扩展

- 2026-08-05 已明确授权增加 S3 兼容对象存储能力和固定六景点介绍 API，且不修改前端页面。
- 视频和海报文件不进入数据库或 FastAPI 容器；后端为管理员生成短时预签名 PUT 地址，上传完成后校验对象元数据并返回长期公开 URL。
- 本地开发使用 MinIO；评委公网演示使用 Cloudflare R2 公共读桶。两者通过同一套 S3 兼容配置切换。
- 只有管理员能够申请上传地址和确认上传；玩家通过公开只读 URL 直接播放媒体。
- 六景点资料为全项目固定、只读、简体中文内容；匿名接口返回路线摘要和单个景点详情，不负责当前位置、解锁状态、GPS 校验或弹框实现。

## 4. 成员 C 的当前职责边界

### 4.1 当前负责

- 剧情节点、选项、章节、结局、视频资源和游戏会话的数据模型。
- 剧情配置的加载、校验和导入格式。
- 开始游戏、读取当前节点、提交选项、恢复状态和结束游戏的后端接口。
- 通用剧情状态机，依据配置跳转，不在接口中硬编码剧情。
- 原型所需的持久化设计、数据库迁移和后端部署适配。
- 接口文档、错误格式、自动化测试和后端冒烟验证。
- 为前端无缝播放提供媒体 URL、海报图和预加载元数据契约。
- 已授权的用户名密码注册、登录、读取当前用户、持久化 Bearer 会话及其数据库迁移；详细契约见 `06-authentication-api-and-persistence.md`。
- 已授权的对象存储预签名上传、上传完成校验、公开媒体 URL 和固定六景点匿名查询接口。

### 4.2 当前不负责

- 六章正式剧情、选项文案和结局文案的创作。
- 剧情视频、海报图和场景插图的制作。
- 播放器、选项覆盖层、动画、页面视觉和国际化实现。
- 浏览器 GPS 定位和地图交互。
- 景点弹框、地图节点点击和前端景点状态管理。
- 一句话短剧、社区、投稿、点赞、管理图表等后续功能。
- 当前阶段的真实 LLM、RAG 和 TTS 接入。

## 6. 第一阶段验收草案

使用一份最小示例剧情验证以下闭环：

1. 匿名体验者能够开始一局游戏。
2. 后端返回入口节点、视频信息和可选项。
3. 提交合法选项后，后端返回配置指定的下一节点。
4. 两条不同选择至少能够进入两个不同节点，并允许后续汇合。
5. 选择历史和当前节点在数据库中可查询。
6. 刷新页面后能够通过会话标识恢复当前进度。
7. 到达结局节点后，会话被标记为完成且不能继续提交普通选择。
8. 非法会话、非法选项、重复选择和缺失剧情节点返回明确的 JSON 错误。
9. 后端可在部署环境启动，并允许部署后的前端域名跨域访问。
10. 管理员可以获得短时上传地址，把 MP4 或海报直传对象存储，并在完成校验后获得长期公开 URL。
11. 公开视频 URL 支持浏览器匿名读取和 HTTP Range 请求，且容器重启后资源仍存在。
12. 匿名用户可以按固定顺序读取六景点摘要，并通过稳定 ID 读取对应详细介绍。

## 7. 已关闭的确认事项

### Q-01 线索和结局规则（已确认）

保留线索机制。部分选择可以发放线索，线索可以影响后续内容或结局；具体配置由剧本编写人员决定。

### Q-02 节点中的非视频内容（已确认）

正式视频内的文字剧情和字幕由视频制作人员处理，不属于成员 C 的实现任务。后端节点不以单独渲染旁白或对白为首版要求。

### Q-03 视频资源交付方式（设计默认）

正式视频尚不存在。后端按媒体 URL 和元数据设计，不把大量视频二进制写入数据库；开发期使用 MinIO，评委公网演示使用 R2。预签名 URL 只用于上传，上传确认返回的长期公开 URL 才能写入剧情 JSON。

### Q-04 会话恢复范围（已确认）

首版采用匿名游戏会话，浏览器保存会话标识，后端持久化进度。只要求同一浏览器恢复，不要求登录和跨设备继续。

## 8. 后续交付顺序

1. 完成待确认事项，冻结第一阶段需求基线。

6. 正式六章内容和视频准备好后，执行数据校验和替换，不重写状态机。
