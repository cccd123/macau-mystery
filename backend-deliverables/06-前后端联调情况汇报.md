# “沉浸式剧本杀游戏”前后端联调情况汇报

> 汇报日期：2026-08-06  
> 汇报对象：组长、前端同学、剧本与视频同学

## 一、当前整体情况

目前“开始游戏 → 播放视频 → 根据选择进入下一段视频 → 到达不同结局”的前后端主流程已经可以跑通，后端返回的视频、选项、线索和结局信息没有发现明显阻塞问题。

当前用于联调的正式剧情配置文件为：

`backend/app/story/scripts/macau_mystery_02.json`

这份剧本当前包含：

- 4 个章节；
- 30 个场景，其中 28 个为普通视频场景，2 个为结局视频场景；
- 20 个视频场景只有一个“继续”选项；
- 最终使用第四章的两个分支作为结局：`fate` 和 `silent`。

也就是说，当前游戏内容已经主要由 JSON 文件控制。视频播放顺序、选项文字、下一段视频、视频 URL、封面 URL 和最终结局，均由该文件配置。

## 二、当前需要处理的几个小问题

### 1. “继续”节点不应该弹出选项

JSON 中一部分视频场景只有一个选项，并且选项文字为“继续”。这类节点的含义是：玩家不需要进行真正的剧情选择，当前视频播放结束后，应当自动进入下一段视频。

当前剧本中共有 20 个此类节点。

前端需要按下面的规则区分：

- 如果当前场景只有一个选项，并且选项文字为“继续”：视频结束后不要显示按钮，直接自动提交该选项并播放下一段视频；
- 如果当前场景存在两个或更多选项：视频结束后再显示选项，让玩家选择；
- 如果当前场景是结局：完整播放结局视频，结束后显示“剧情结束”等结算内容。

需要特别说明：前端不能只读取 JSON 中的 `next_scene` 后自行切换视频。即使是“继续”，也需要调用后端的选择接口，让后端记录进度并返回下一个正式场景。这样才能保证刷新恢复、线索发放和结局判断不会出错。

建议的播放过程如下：

```text
当前视频播放结束
        ↓
判断当前场景的选项数量和文字
        ↓
只有一个“继续” ── 自动调用选择接口 ── 播放下一段
        ↓
有多个真实选项 ── 弹出选项 ── 玩家选择后播放下一段
        ↓
结局场景 ── 播放结局视频 ── 显示结束页面
```

目前前端仍会把“继续”当作普通选项显示，而且在视频结束前还提供了手动“显示选项”的入口，这与沉浸式体验的预期不一致，需要调整。

### 2. `poster_url` 已接入播放器，但目前没有真正发挥作用

**如果没有不可接受的卡顿，保持当前实现即可，跳过此问题**



每个视频场景都有一个 `poster_url` 字段。它表示视频的封面图，浏览器在视频尚未开始播放或仍在加载时会先显示该图片。

这个字段的主要作用是：

- 减少视频切换时的黑屏感；
- 在下一段视频尚未加载完成时保持画面；
- 网络速度较慢时，让用户看到对应场景画面，而不是空白播放器。

当前前端已经把 `poster_url` 传给了视频播放器，因此并不是完全没有接入。但是目前 30 个场景的 `poster_url` 全部指向同一张 `default_poster.jpg`，这张图片又是黑色图片，所以实际体验仍然接近黑屏，无法体现每一段视频的画面衔接。

如果要真正利用这个字段，需要：

1. 为每个视频片段制作一张对应封面图，建议使用该视频的第一帧或最接近第一帧的清晰画面；
2. 图片比例尽量与视频一致，避免切换时出现拉伸或画面跳动；
3. 将图片上传到 Vercel Blob；
4. 把每个 JSON 场景中的 `poster_url` 替换成对应图片的公开 URL；
5. 前端切换场景时立即显示下一段的 poster，再开始播放视频。

注意：poster 可以改善“等待时看到什么”，但不能代替视频预加载。要真正缩短等待时间，仍需要配合下一节的预加载机制。

### 3. 媒体资源已从 MinIO 调整为 Vercel Blob

原方案使用 MinIO 存放视频和图片，但 MinIO 需要额外部署服务、维护存储桶和配置公网访问，演示环境部署成本较高，因此当前正式联调内容已经改用 Vercel Blob。

仓库中仍保留了 MinIO/S3 兼容上传相关代码和配置，但它不再是当前剧情媒体的主要交付方式。

### 4. 视频跳转存在加载延迟，需要前端预加载

联调中发现，从一个视频选择进入下一段时，会出现短暂等待或加载画面。主要原因是：当前前端通常在玩家做出选择、后端返回新场景之后，才开始请求下一段视频。

实际上，后端已经在每个选项中返回了候选下一场景的 `preload` 信息，其中包括下一段视频和 poster 地址。当前前端虽然定义了这些字段，但还没有实际使用它们进行预加载。

建议前端采用以下方案：

- 当前视频开始播放后，立即读取所有选项中的 `preload` 信息；
- 对可能进入的下一段视频提前创建隐藏的预加载任务；
- 对只有“继续”的场景，应优先完整预加载唯一的下一段视频；
- 对有 2～3 个分支的场景，可以同时预加载候选视频，或者至少先加载视频开头和元数据；
- 玩家选定分支后，立即显示下一段对应的 poster，并切换到已经预加载的视频；
- 切换期间保留加载提示和重试机制，避免网络异常时页面无响应。

简单理解就是：用户在看当前视频时，浏览器已经在后台准备下一段视频。这样当前视频结束后就能更快衔接，而不是等玩家选择以后才开始下载。

## 三、补充

### 1. 修改 JSON 后需要重新导入并发布

后端运行游戏时读取的是数据库中的已发布剧情版本，不会持续监听磁盘上的 JSON 文件。因此，修改 `macau_mystery_02.json` 后，不能只替换文件就认为线上游戏已经更新，还需要执行“校验、导入、发布”。
