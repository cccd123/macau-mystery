# 《澳门悬案》剧情和视频制作交付指南

这份指南写给剧情编写者和视频制作者。

你不需要会编程。最后只需要交给成员 C 三样东西：

1. 剪辑好的剧情视频；
2. 每段视频的一张封面图；
3. 一份说明“玩家选择后应该播放哪段视频”的 JSON 文件。

JSON 看起来像代码，但不需要从头手写。正确做法是：先填写剧情表格，再让 AI 按照表格生成 JSON，最后检查视频名称和跳转关系。

---

## 一、游戏是怎样播放剧情的

### 1. 一段视频播放完，再让玩家选择

不要把整个故事导出成一条长视频。每当剧情需要玩家选择时，就把视频切开。

例如：

```text
播放视频 A：老伯拿出一封旧信
        ↓
视频 A 播放完，画面停在老伯拿着信的镜头
        ↓
出现两个选项：
“调查旧信”       “询问妈阁庙历史”
        ↓                    ↓
播放视频 B              播放视频 C
```

视频 A、B、C 都是单独的 MP4 文件。

### 2. 每个选项都要说明下一段播放什么

剧情人员需要写清楚：

| 当前视频         | 玩家选择    | 下一段视频                |
| ------------ | ------- | -------------------- |
| ch01_s01.mp4 | 调查旧信    | ch01_s02_letter.mp4  |
| ch01_s01.mp4 | 询问妈阁庙历史 | ch01_s02_history.mp4 |

不同分支以后可以回到同一段剧情。例如，不管玩家调查旧信还是询问历史，最后都可以前往亚婆井。这样不用为每条路线制作六章完全不同的视频。

### 3. 某些选项可以奖励线索

线索就是系统替玩家记住的重要发现。

```text
玩家选择“调查旧信”
→ 播放调查旧信的视频
→ 同时获得“旧信残片”线索
```

线索可以影响后面的剧情或结局：

```text
拥有“旧信残片” → 播放完整揭开真相的结局
没有“旧信残片” → 播放没有查清真相的结局
```

剧情人员只需决定：

- 哪个选项会获得线索；
- 线索叫什么；
- 获得哪些线索后进入什么结局。

成员 C 负责让系统记录和判断。

### 4. 系统可以自动判断结局

玩家完成最后一段剧情后，系统可以检查已经获得的线索，然后自动播放对应结局。

```text
玩家点击“揭开真相”
        ↓
系统检查：有没有“旧信残片”？
        ↓
有 → 播放 ending_good.mp4
没有 → 播放 ending_bad.mp4
```

JSON 中把这种自动判断叫做 router。可以把它理解成“看不见的分路路口”。它不需要制作视频，玩家也看不到。

## 二、AI生成JSON前需要准备哪些材料

### 1. 剧情分支表

建议用 Excel 或在线表格填写。一个选项填写一行：

| 当前视频编号           | 选项文字    | 选择后进入的视频编号       | 获得的线索           |
| ---------------- | ------- | ---------------- | --------------- |
| ch01_s01         | 调查旧信    | ch01_s02_letter  | letter_fragment |
| ch01_s01         | 询问妈阁庙历史 | ch01_s02_history | 无               |
| ch01_s02_letter  | 继续追查    | final_router     | 无               |
| ch01_s02_history | 尝试揭开真相  | final_router     | 无               |

还需要一张线索表：

| 线索编号            | 玩家看到的名称 | 说明                |
| --------------- | ------- | ----------------- |
| letter_fragment | 旧信残片    | 残片上写着“某年春，自妈阁启程”。 |

编号只给系统使用，必须使用小写英文、数字和下划线。

### 2. 剧情视频

一个可以播放的剧情节点对应一个视频文件：

```text
ch01_s01.mp4
ch01_s02_letter.mp4
ch01_s02_history.mp4
ending_good.mp4
ending_bad.mp4
```

文件名就是视频编号。表格、视频文件和 JSON 必须使用完全相同的编号。

### 3. 视频封面图

每段视频配一张同名图片：

```text
ch01_s01.mp4
ch01_s01.jpg

ch01_s02_letter.mp4
ch01_s02_letter.jpg
```

封面图用于视频加载时显示画面。网络较慢时，用户不会只看到空白播放器。

### 4. 可以直接打开的视频地址（暂不需要，AI生成JSON时告诉AI“URL字段暂时不需要填写”）

网页不能读取制作人员电脑桌面上的视频。视频需要上传到成员 C 或部署人员提供的位置。

上传完成后，会得到这样的地址：

```text
https://media.example.com/macau/v1/ch01_s01.mp4
```

请在浏览器无痕窗口打开地址：

- 能直接播放视频：可以使用；
- 打开网盘分享页、登录页或提示没有权限：不能使用。

大量正式视频不要提交到 Git 项目仓库。

### 5. 最终 JSON 文件

JSON 是一张“系统能看懂的剧情路线图”。制作人员只需要认识下面几项：

| JSON 名称     | 实际意思       |
| ----------- | ---------- |
| id          | 这段视频或选项的编号 |
| video_url   | 视频的网络地址    |
| text        | 玩家看到的选项文字  |
| next_scene  | 点击后进入哪个视频  |
| grant_clues | 点击后获得什么线索  |

AI 可以根据剧情分支表生成 JSON，制作人员负责核对。

## 三、视频和图片应该怎样制作

### 1. 推荐的视频设置

在剪映、Premiere、达芬奇等软件中导出时，建议统一使用：

| 项目    | 推荐设置                     |
| ----- | ------------------------ |
| 文件格式  | MP4                      |
| 视频编码  | H.264                    |
| 音频编码  | AAC                      |
| 画面比例  | 16:9 横屏                  |
| 分辨率   | 1920 × 1080              |
| 帧率    | 全部使用 25 fps，或全部使用 30 fps |
| 音频采样率 | 48 kHz                   |

如果已经决定使用竖屏，也必须全部统一为同一种比例，并提前告诉成员 C。不要在同一个故事中混用横屏和竖屏。

### 2. 文件应该怎样命名

正确示例：

```text
ch01_s01.mp4
ch01_s02_letter.mp4
ending_good.mp4
```

不要使用：

```text
第一章最终版.mp4
最终修改2.mp4
这个才是最后版本.mp4
```

命名规则：

- 使用小写英文、数字和下划线；
- 不使用中文、空格和括号；
- 视频、封面、表格和 JSON 使用同一个编号；
- 已经交付的编号不要随意修改。

### 3. 每段视频的结尾要注意什么

选项会显示在上一段视频的最后画面上，所以结尾需要这样处理：

- 最后约 0.5 至 1 秒保持相对稳定的画面；
- 不要淡出到黑屏；
- 不要加入片尾字幕、Logo 或“未完待续”；
- 不要停在闪白、快速运动或人物闭眼的瞬间；
- 尽量在画面中留出放置选项的空间；
- 如果画面里有人物，最好让人物自然停顿，像是在等待玩家回答。

例如，老伯拿出旧信后，让镜头在“老伯拿着信”的画面稳定片刻再结束。选项出现时，背景仍然是剧情画面。

### 4. 下一段视频的开头要注意什么

- 直接进入剧情，不加黑场和重复片头；
- 人物位置、服装、光线尽量连续；
- 环境音和音乐音量不要突然跳变；
- 开头可以保留约 0.3 至 1 秒与上一段相近的画面；
- 玩家点击选项后，应马上看出新视频是在回应刚才的选择。

例如：

```text
上一段结尾：老伯拿着旧信。

选择“调查旧信”：
下一段先保持旧信近景，然后开始检查信件。

选择“询问历史”：
下一段仍从老伯拿着信开始，随后老伯收起信并讲历史。
```

### 5. 封面图规范

- 建议使用 JPG；
- 推荐尺寸 1920 × 1080；
- 比例与视频一致；
- 选择清晰、能代表当前剧情的一帧；
- 文件名与视频相同；
- 不带水印、黑边和制作备注。

## 四、从制作剧情到交给成员 C：完整例子

### 第一步：写出简单的剧情路线

```text
老伯拿出旧信
├── 调查旧信 → 获得“旧信残片”
└── 询问妈阁庙历史 → 没有获得线索

最后系统判断：
├── 有“旧信残片” → 好结局
└── 没有“旧信残片” → 坏结局
```

### 第二步：给每段剧情起编号

| 剧情内容     | 编号               |
| -------- | ---------------- |
| 老伯拿出旧信   | ch01_s01         |
| 调查旧信的剧情  | ch01_s02_letter  |
| 询问历史的剧情  | ch01_s02_history |
| 系统自动判断结局 | final_router     |
| 好结局      | ending_good      |
| 坏结局      | ending_bad       |

final_router 只是判断规则，不需要制作视频。

### 第三步：剪辑和导出

需要制作：

```text
videos/
├── ch01_s01.mp4
├── ch01_s02_letter.mp4
├── ch01_s02_history.mp4
├── ending_good.mp4
└── ending_bad.mp4

posters/
├── ch01_s01.jpg
├── ch01_s02_letter.jpg
├── ch01_s02_history.jpg
├── ending_good.jpg
└── ending_bad.jpg
```

### 第四步：上传视频和图片

假设成员 C 提供的上传地址是：

```text
https://media.example.com/macau/v1/
```

上传后得到：

```text
https://media.example.com/macau/v1/ch01_s01.mp4
https://media.example.com/macau/v1/ch01_s01.jpg
https://media.example.com/macau/v1/ch01_s02_letter.mp4
https://media.example.com/macau/v1/ch01_s02_letter.jpg
```

其他文件按相同规则上传。

### 第五步：整理给 AI 的资料

把下面的内容和全部视频地址一起提供给 AI：

```text
故事名称：跨越中葡的悬案
入口视频：ch01_s01

ch01_s01：
- 选“调查旧信”进入 ch01_s02_letter，并获得 letter_fragment
- 选“询问妈阁庙历史”进入 ch01_s02_history，不获得线索

ch01_s02_letter：
- 选“继续追查”进入 final_router

ch01_s02_history：
- 选“尝试揭开真相”进入 final_router

final_router：
- 有 letter_fragment 进入 ending_good
- 其他情况进入 ending_bad

线索：
- letter_fragment，名称“旧信残片”，说明“残片上写着某年春，自妈阁启程。”

视频和图片地址：
【粘贴上传后的全部地址】
```

### 第六步：让 AI 生成 JSON

复制下面的提示词：

```text
请把我提供的互动视频剧情资料整理成可以直接交给后端成员 C 的 JSON。

要求：
1. 只输出 JSON，不写解释。
2. 根对象包含 schema_version、story_id、title、description、entry_scene、chapters、clues。
3. 普通视频节点的 type 是 video，包含 id、media、choices。
4. 结局节点的 type 是 ending，包含 ending_code、media，choices 必须是空数组。
5. 自动判断节点的 type 是 router，包含 routes，不需要视频。
6. 每个 media 包含 status、video_url、poster_url、mime_type、duration_ms。
7. 每个选项包含 id、text、next_scene、grant_clues。
8. 所有 next_scene 必须对应真实存在的场景 id。
9. grant_clues 中使用的线索必须在 clues 中定义。
10. 不要添加旁白、对白、字幕或照片识别字段。

以下是剧情资料：
【粘贴上一步整理的全部内容】
```

### 第七步：检查 AI 生成的 JSON

不需要看懂每一行，只检查四件事：

1. 选项文字是否正确；
2. next_scene 是否是正确的下一段视频编号；
3. 需要奖励线索的选项是否填写了 grant_clues；
4. video_url 和 poster_url 是否能够打开。

例如：

```json
{
  "id": "inspect_letter",
  "text": "调查那封旧信",
  "next_scene": "ch01_s02_letter",
  "grant_clues": ["letter_fragment"]
}
```

这段翻译成人话就是：

```text
玩家看到“调查那封旧信”；
点击后进入 ch01_s02_letter；
同时获得 letter_fragment 线索。
```

### 第八步：交给成员 C

最终交付：

```text
macau_mystery_01_v1/
├── macau_mystery_01.json
├── 剧情分支核对表.xlsx
└── 制作说明.md
```

视频和图片已经上传，不需要放进 Git。制作说明中写清：

```text
版本：v1
交付日期：2026-08-03
视频状态：全部完成
未完成内容：无
上传目录：https://media.example.com/macau/v1/
```

成员 C 会用程序检查 JSON。如果提示“找不到下一场景”，通常是某个 next_scene 写错；如果提示“找不到线索”，通常是 grant_clues 中的线索编号没有定义。

## 五、交付前检查清单

- [ ] 所有视频都是 MP4，比例和分辨率统一。
- [ ] 每段视频都有同名 JPG 封面。
- [ ] 视频结尾没有黑屏，并保留了稳定画面。
- [ ] 分支视频开头能够自然承接上一段。
- [ ] 视频和图片地址在无痕窗口中可以直接打开。
- [ ] JSON 中的选项文字与剧情分支表一致。
- [ ] 每个 next_scene 都对应真实存在的节点。
- [ ] 每个线索编号都已定义。
- [ ] 至少有一个能够到达的结局。
- [ ] JSON 文件使用 UTF-8 编码，文件名为 macau_mystery_01.json。

以上内容全部通过后，就可以交给成员 C。
